# Event-driven destination routing — research and contract, 2026-10-29

Owner: Pretend Internet, issue #12. This implementation follows the user's later authorization to build universal event-kind routing; the earlier four-app matrix is not an implementation prerequisite. No app source is imported and no public test publication is authorized.

## Primary evidence and reuse decision

Inspected current primary specifications on 2026-10-29:

- [NIP-01](https://github.com/nostr-protocol/nips/blob/master/01.md): kinds are integers 0–65535, extensible without a central registry. Persistence conventions distinguish regular, replaceable, ephemeral and addressable events. OK acknowledges acceptance, not durable delivery. Some numeric ranges have unspecified persistence; do not invent it.
- [NIP-11](https://github.com/nostr-protocol/nips/blob/master/11.md): optional HTTP metadata at the relay WebSocket URI with `Accept: application/nostr+json`. `limitation` is singular. Frame limits count UTF-8 bytes including the EVENT envelope; content limits count Unicode characters. Supported NIPs do not constitute an accepted-kind whitelist. Authentication, payment, PoW and restricted writes need separate handling. Timestamp-limit interpretation is insufficiently specified here, so preserve those claims without treating them as guaranteed cutoffs.
- [NIP-65](https://github.com/nostr-protocol/nips/blob/master/65.md): signed kind 10002; markerless r tags mean both read/write. Author write relays and mentioned users' read relays are distinct delivery groups. Missing metadata must not disable routing.
- [NIP-66](https://github.com/nostr-protocol/nips/blob/master/66.md): signed 30166 reports carry repeated k/!k, N, R and RTT tags. Attribution is not truth; absence cannot block connections and one monitor cannot exclude the network. Reports remain advisory even when multiple monitors agree. Select latest report per monitor+relay, reject invalid/future/stale events, retain conflicts.
- [NIP-42](https://github.com/nostr-protocol/nips/blob/master/42.md): challenge-bound AUTH is connection-local, not ordinary publication. External signer capability only; verify returned challenge, relay, identity and signed template.
- [NIP-17](https://github.com/nostr-protocol/nips/blob/master/17.md), [NIP-59](https://github.com/nostr-protocol/nips/blob/master/59.md): gift-wrap recipients' kind 10050 inbox lists require a separate destination policy. Generic publication cannot infer every future kind's privacy or application semantics. Require explicit destinations for private events; never fallback to public discovery. Auth-token kinds are rejected by the ordinary EVENT publisher.
- [Blossom BUDs](https://github.com/hzrd149/blossom): BUD-03 supplies signed 10063 server lists; BUD-04 mirrors existing blobs; BUD-06 HEAD upload checks hash/type/length without sending payload bytes and does not guarantee PUT success; BUD-07 distinguishes payment-required from transport failure; BUD-11 authorization remains with the consumer's signer/uploader. The sibling preflight helper accepts arbitrary MIME types and sizes, not app categories.

## Frozen v1 contract (before implementation)

`RelayRouter` takes bootstrap relays and optional pinned/allowed destinations, clock, network implementation, external AUTH signer and registry. `discover(signedEvent, options)` reads bounded signed metadata plus NIP-11, then `plan` selects for the actual event. `publish(signedEvent, options)` explicitly executes publication, re-plans after discovery, tries bounded fallbacks and returns per-destination acceptance/readback evidence. Calling discover/plan never publishes a probe event or requests a signer.

All valid kinds, including unknown/future kinds, use the same envelope and policy evaluation; no app-name or fixed workload switch. Classification covers NIP-01 persistence only; it does not claim to implement every application NIP. For public publication, create independent author and mentioned-recipient delivery groups. For private or gift-wrapped publication, restrict writes to explicit approved destinations (no public metadata lookup for private policy). Authentication event kinds 22242/24242/27235 must use their dedicated transport, not this publisher.

Registry records: canonical URL; sanitized NIP-11 policy + fetch time; latest signed monitor claims per monitor; locally observed attempt scoped to event ID, author, kind and authenticated principal; bounded TTL. Persist only normalized claims and outcome codes, never event bodies, raw rejection text, AUTH events or secrets. Cache generic rejects by exact event+principal. An explicit unsupported-kind prefix can temporarily suppress that author/kind/principal at that relay; never infer a kind-wide ban from free-form rejection prose. Malformed metadata is ignored/diagnosed, never a hard exclusion claim. Local snapshot import validates normalized fields; the caller-owned cache is a local trust boundary, not a signed remote data source. Network monitor ingestion always verifies signatures.

Decision: event ID/kind/class/frame bytes, generation time, per-group selected/fallback URLs and reasons, excluded destinations with stable reasons, metadata warnings and unverified status. Order within an eligible delivery group: explicit preference, fresh verified same-kind publication evidence for this principal, corroborated kind-specific hints, current direct metadata, RTT, URL. Monitor scores are bounded, never exclusion gates; kind hints must not penalize unrelated kinds. Fresh direct hard limits, missing auth/payment entitlement, private boundary and exact-event cooldown can exclude. Unknown policy is attemptable, not verified writable.

Publication: same signed event on every attempt, no event mutation or resigning. One bounded attempt per destination per call; one NIP-42 handshake retry on the same connection. Store rejection categories without assuming a human message proves a permanent kind restriction. Durable event success requires exact signed event ID readback; ephemeral success is acceptance-only and explicitly says persistence is not expected. Readback failure is partial, never verified. Redundancy means distinct URLs; independence of operators is not inferred. Failure in one recipient delivery group cannot be masked by author acceptance.

Network work has endpoint/event/byte/time/concurrency caps. Discovered URLs must pass destination policy before any request; no userinfo/query credentials or local-address discovery. Server deployments must additionally enforce an egress allowlist/DNS policy. No optional monitor, catalog or remote control plane is a required dependency. Existing apps remain independent; this standalone tool is not a shared app runtime or a retrofit of rejected source.
